# 集水坑泵保护控制：回差、时间窗、应急覆盖

本文档固化两条有争议的策略选择，并描述落盘与恢复语义。实现是纯策略
（`tunnelnet/drain/protect.py`）加控制器（`tunnelnet/drain/sump.py`），
事件日志与投影分别在 `journal.py`、`drainage.py`。

## 1. 三条水位线（回差）

不再用单阈值，改为满足
`停止水位 < 启动水位 < 危急水位` 的三条线：

| 水位区间 | 泵停时 | 泵运行时 |
| --- | --- | --- |
| `level <= 停止水位` | 保持停 | **停泵** |
| `停止水位 < level < 启动水位`（回差带） | 保持停 | 继续运行 |
| `启动水位 <= level < 危急水位` | 按时间窗决定 | 继续运行 |
| `level >= 危急水位` | 见第 2 节，安全覆盖 | 继续运行 |

水面在启停线附近晃动时，泵只在「越过启动线」与「越过停止线」两个沿上
动作，回差带内的抖动不产生任何启停。

## 2. 保护期内水位继续涨：选「分级覆盖」这一种

两种纯策略的取舍：

* **等到保护结束**：最大限度护泵；但极端进水时泵干等着，可能淹井。
* **强行启泵**：最大限度防汛；但泵可能在热态、最小间隔内反复启停，
  正好把原来的打泵问题换个方式找回来。

**本实现只采用一种规则——分级（普通线等待，危急线覆盖）：**

1. 保护期内水位只到普通启动线：**一律等到保护结束**，到期后的下一个
   液位采样自动启泵。等待期间只记一次 `start_blocked` 审计（同一波高
   事件沿只记一次，液位回落会重新布防，避免日志被水面波纹刷爆）。
2. 另设一条物理上更高的**危急水位**（不是启动线上的小偏移）。水位
   达到危急线，且泵未运行时，**安全覆盖时间类保护窗**（冷却窗、启动
   失败退避窗），立即强启，并写 `pump_start_emergency` 应急审计，事后
   可单独统计应急次数。
3. **故障锁（FAULT）不被任何水位覆盖**。连续启泵失败达到上限后进入
   故障锁，此时即使越过危急线也只报 `fault_alarm`、不启泵——对已知
   起不来的泵强启，护泵和防汛两边都不成立；必须人工检修后
   `reset_fault()` 复位。

防汛侧的剩余风险用「危急线必须保守设置 + 故障报警即出抢险单」兜底。

## 3. 重叠的保护窗口：取并集（max），不累加

任一时刻一台泵只有一个有效窗口：

* 同类型/不同类型的时间窗重叠（如冷却窗未完又叠加退避窗）：
  **结束时刻取两者最迟者**，窗口时长不累加、不滚动延长。
* 等长合并时后进入的原因生效（原因强度：故障锁 > 启动失败退避 > 冷却）。
* 故障锁一旦置位（`until = ∞`），覆盖一切时间窗，且只能由人工复位
  解除；复位同时清零失败计数。

冷却窗在每次**正常停泵**后重新布置（最小间隔 = 两次启动之间的最短
时间）。

## 4. 启停失败的恢复

* **启泵失败**：执行器抛异常即计入 `failed_attempts`，布置指数退避窗
  （`min_interval × 2^(n-1)`，封顶 `backoff_cap`），窗内按 `blocked`
  处理、到期下个采样自动重试；成功启动后失败计数清零。达到
  `max_attempts`（默认 3）后进入故障锁并报警。
* 危急水位可以提前结束退避窗立即再试；若这次仍失败，同样累计失败
  次数，第三次仍进故障锁。
* **停泵失败**：泵的真实状态未知，按「仍在运行」保守处理并记
  `stop_failed` 报警，不会在未知状态下再发启动令。

## 5. 状态机与时序依赖

```
stopped ──(level≥启动线/人工请求, 无窗)──> running
stopped ──(有需求但在窗内)──> blocked(沿事件) ──窗到期+采样──> stopped→running
stopped ──(危急水位, 时间窗内)──> running(应急, 清除时间窗)
running ──(level≤停止水位, 停泵成功)──> stopped + 布置冷却窗
stopped ──(启泵失败×n<上限)──> backoff ──到期重试──> running / stopped
任何态  ──(第 max_attempts 次失败)──> FAULT(∞) ──人工复位──> stopped
```

人工启动请求与自动需求共用同一套保护判定（不会绕窗），区别仅是
人工请求在任意水位产生启动需求。

## 6. 幂等与持久化

* **请求幂等**：`request_start(request_id)` 对同一 `request_id` 只产生
  一次泵动作，重复请求直接返回首次决策（最近 64 个 id 随状态落盘）。
  无 id 的重复调用则由状态机本身保证：泵已在运行 → `hold`，不会二次
  打泵。
* **落盘**：每个集水坑两份记录，均经原子替换写入（临时文件 +
  `os.replace`），事件追加后 fsync：
  * `sump-state/<pit>.json`：当前液位、泵运行态、有效保护窗（含
    `until=∞` 的故障锁）、当前运行起止指针、失败计数、已见请求。
  * `sump-journal/events-<pit>.json`：只追加的事件日志。
* **跨重启**：控制器构造时读回状态——在运行的泵按仍在运行处理，
  冷却/退避/故障窗按 `until` 原样恢复并写一条 `state_recovered` 审计；
  进程崩溃在「泵已起、状态未存」之间时，由下一次液位采样自然纠偏。
  液位和泵状态永远以盘上的这一份为准。

## 7. 排水记录与审计同一份口径

`drainage.py` 不存任何自有事实：排水运行记录（`DrainageRun`）和审计
条目（`AuditEntry`）都是**同一本事件日志的两个投影**
（`build_report(events)`）。每条审计 `id = <pit>-<12位序号>` 直接指回
事件序号；启/停配对只认日志中的 `pump_start(_emergency)` 与
`pump_stop`/失败事件，崩溃留下的开放运行显示为 `running` 而不会丢。
报表与审计因此不可能对同一次排水给出不同数字。

## 默认参数

`SumpConfig(start_level=0.80, stop_level=0.30, emergency_level=1.20,
min_interval=300s, max_attempts=3, backoff_factor=2, backoff_cap=1800s)`
构造时强制校验三条线严格递增，配错直接 `ValueError`。
